# 木与光 · 可编辑装修模拟器

Angular 22 + Three.js，显式使用 WebGL2。三套 Blender / GLB 户型模型，原始清水房、方案一、方案二及已有布置共用左侧方案列表、新建入口和编辑页面。旧清水房工作台链接兼容，自动迁入已有本机方案，保留备份。

- 原始户型 · 清水房：3米层高，62条墙体/护栏记录，支持灰色隔墙及门窗的可视化编辑，详见 RAW-SHELL.md。
- 方案一：保留原方案、12 个空间、121 组家具，光厅仅加可移动绿植。
- 方案二：按新增平面图重建户内空间，11 个空间、78 组家具；不包含电梯间、楼梯间、入户光厅。延续白色沙发、蛋黄单椅、黑色正方茶几、淡蓝岛台与不锈钢厨房台面。
- 方案二修订 2：电视后增加约 3.4m 长的整排白柜；手工区与次卧之间开白框玻璃内窗（宽约 1.02m、高 1.20m、窗台高 1.10m），次卧相邻柜体改为 0.88m 高窗下柜；补回厨房北侧的玄关凹位、地面、墙体与 L 形收纳柜。尺寸为模型估算。
- 家具布置和房间状态分别自动保存，刷新后恢复上次选中的方案。切换不会覆盖另一套存档；撤销历史只针对当前加载的方案。
- 两套方案的窗外均加入 7 棵大树（南侧 4 棵、北侧 3 棵），仅在“第一人称漫游”时显示；自由查看、户型图、房间空间视角及室内视角均隐藏。退出漫游立即隐藏，清水房状态下进入漫游仍可看到树冠。
- 导出文件名包含方案名称；导入 JSON 时需切换至对应户型，错误户型的文件会被拒绝且不修改当前布置。

## 使用

- 左侧方案区位于房间导航上方，按文件列表显示所有方案；单击打开并高亮当前方案，可折叠列表，方向键定位、Enter打开。标题旁提供新建和刷新。保存状态显示在列表下方。顶部栏高度48px，手机通过左上角“方案与房间”按钮打开侧栏。

- 右上角依次是“自由查看”“户型图”“第一人称漫游”；左侧保留各房间导航。每间房另有空间视角和室内视角。
- 左侧眼睛控制房间可见性，座椅按钮控制该房间装修。
- 底部“隐藏最近墙面”左侧是“锁定物件”，默认关闭。开启后取消当前选择，画面和家具清单都不能选中家具，也暂停添加和拖动；镜头仍可旋转、平移与缩放。关闭后恢复操作。锁定作为临时浏览状态在两套方案切换时保持，刷新网页恢复不锁定，不改动家具存档。
- “清水房”隐藏家具、柜体、灯具、软装和地面面层，墙体改为水泥基底；门窗与结构保留。
- “隐藏最近墙面”只移除当前视线首先遇到的一组墙及关联窗框、横梁，保留后方墙体。旋转或平移视角后重新选择最近墙面，不会逐层剥除远墙。俯瞰视角按视线的平面投影判断；平面图墙体裁切至低位。
- 天花板默认不显示，独立使用“显示天花板”开关；关闭自动隐藏墙面也不会打开天花板。平面图始终隐藏天花板。
- 编辑模式下直接拖动家具，按 5 cm 网格吸附；空白处左键拖动旋转视角。按住鼠标中键或右键拖动平移，滚轮缩放；中键拖动不会移动家具。
- 点击画面右上角“第一人称漫游”，每次固定从当前方案的入户门外开始、面向屋内，按 W 可穿过门洞进入玄关；不受此前查看哪个房间影响。视线高度 160 cm，W/S 前进后退、A/D 左右平移，鼠标转向；速度固定为 2.8 米/秒，Shift 不改变速度。Esc 退出并恢复进入前的视角。两套方案都可使用。
- 漫游时提供门外的小块落脚地面并连通门槛处楼板，仅用于进门浏览，不扩建方案二忽略的光厅或公共区域；退出漫游后隐藏。
- 漫游期间暂停家具选择和拖动、保留完整墙面；退出后恢复原来的墙面隐藏设置，天花板开关保持原状。支持墙体、窗户及户型边界阻挡和沿墙滑行；门洞可通行，家具和门扇暂不做碰撞，便于查看布局。
- 浏览器若不支持或拒绝锁定鼠标，会显示提示并改用左键拖动转向；仍支持 WASD。切出窗口或标签页会清除移动按键，切换方案会退出漫游。该模式使用键盘与鼠标，手机仍可使用原有触控浏览。
- 点击家具后可调整 X / Z 坐标、旋转、比例、配色，复制或删除。选择任一部件都会选中整件家具：洞洞板包含 56 个孔点；冰箱包含柜体、门面与分缝；灯具、电视、窗帘等同样整体操作。两把办公椅与三盆光厅绿植各自独立。
- 12 款内置样式涵盖沙发、单椅、方茶几、圆餐桌、床、斗柜、绿植，点击添加或拖入空间。
- Ctrl/⌘ + Z 撤销，Ctrl/⌘ + Shift + Z 重做，Delete 删除；保留最近 60 次操作。
- 登录后，当前布置自动异步保存至 Supabase，同时保留当前浏览器的 localStorage 缓存。JSON 导出/导入适用于本模型版本，可长期备份。
- 方案二旧存档和 JSON 自动升级至 modelRevision 2，补上两组新柜；已有家具的移动、复制、删除、颜色及房间状态保留。未移动的电视与洞洞板会调整到新的默认位置，手动移动过的物件保持原位。升级前的自动存档备份在原存储键后加 `:before-model-revision-2`，更新后的存档不会重复添加柜子。
- 家具分组修订版使用 JSON 格式 v2，旧版 v1 方案自动整合。旧部件的位置、角度、比例会转换为完整家具的变换；复制过的零件会成为完整家具副本。如果同一家具多个旧部件各自有冲突编辑，优先采用已编辑的主体，再采用其他已编辑部件的变换。原自动存档保留备份，右侧可下载；原有独立家具、样式库家具和房间开关会保留。
- “导出当前 GLB”保存当前位置、旋转、缩放、配色及房间显隐状态；自动遮挡墙不会被误当作删除。完整顶板会重新纳入 GLB。
- “恢复初始布置”可撤销。前端可静态部署，账号与云端方案通过 Supabase 提供。

## Supabase 云端方案与登录

连接信息位于 `src/environments/environment.ts`，已配置本项目的 URL 和 publishable key。前端使用 Supabase Auth 邮箱/密码登录，方案通过 REST API 和数据库函数保存。publishable key 可以放在浏览器中，数据权限由数据库 RLS（行级安全策略）控制，详见 [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)。

### 首次配置

1. 在 [项目 SQL Editor](https://supabase.com/dashboard/project/nbdodqezyijrztikvkcd/sql/new) 依次执行 `supabase/migrations/202609150001_home_design_schemes.sql` 和 `supabase/migrations/202609150002_unified_floor_plans.sql`。已配置的数据库只需执行第二个脚本以支持原始清水房；脚本可重复执行，不清空已有数据，也不改变权限与冲突保护。
2. 在 Supabase **Authentication → Users** 中使用已有邮箱/密码用户，或由项目管理员添加用户。确认 Email 登录已启用且账号可正常登录。网页目前提供登录/退出入口，未提供注册入口。
3. `npm run build` 后按原方式部署到 EdgeOne Pages。打开网页，游客可浏览；点击“登录编辑”，编辑后方案列表下方应显示“已保存到云端”。用另一个浏览器打开网页，可查看同一方案。

建表必须使用 SQL Editor 或已有数据库管理连接；publishable key 无法执行建表。若表/函数不存在，页面会提示“云端方案库尚未初始化”，不会把上传失败显示为成功。

### 访问规则与使用

- 所有方案使用同一个列表与管理器；保存位置属于方案状态。旧本机方案保留本机编辑权限，迁入时不自动上传。登录后可将当前本机方案另存共享副本，原稿保留。原始户型同步前需完成上述第二个数据库迁移。

- 所有人均可读取所有云端方案；**任一正常登录用户均可修改所有共享方案**，不是按账号隔离。Supabase 的匿名登录用户也被数据库策略禁止写入。
- 游客可查看房间、切换装修显示和漫游，这些浏览操作只临时影响当前画面；不能添加、移动家具、新建、导入或提交方案。
- 左侧“方案”旁的新建按钮支持命名并复制当前布置，也可从任一户型的初始布置开始。每个方案有独立 ID、家具与房间状态。暂不提供方案删除，数据库也未授予客户端 DELETE 权限。
- 完成拖动、修改参数、換色、添加/复制/删除家具、导入、撤销/重做、恢复初始布置及房间状态切换后，500 ms 防抖异步上传；持续操作最长约 2 秒触发一次保存。上传不中断三维操作，同一方案按顺序提交，切换方案会立即发起待保存请求。
- 断网时保留本地待同步记录，按退避间隔自动重试；恢复联网或点击“重试保存”立即重试。刷新页面会恢复待同步布置；退出登录后停止新增上传，重新登录继续同步。关闭页面前写入本地缓存，下次打开并登录补传，不依赖浏览器关闭时一定能发出网络请求。
- 方案列表下方显示当前方案状态和所有待同步方案数量。多设备同时修改同一方案时，通过数据库版本号阻止覆盖；点击“另存本地副本”将当前本地修改存为新方案。没有自动合并家具位置；其他设备的最新修改在切换方案、刷新页面或点击“刷新方案”后读取。
- 原来的两个 localStorage 存档键继续兼容，首次登录加载无云端布置的户型时会上传原布置。若云端已有内容，优先加载云端；替换前的本地布置备份在原存储键后加 `:before-cloud`。本地缓存不可用时会显示导出备份提示。
- 云端保存方案名称、所属户型、布局 JSON、版本、修改时间和用户 ID；GLB 模型仍随静态站点分发。导出 JSON / GLB 功能保留。

## 开发和构建

推荐使用 Node.js 24.18.0，与 `.nvmrc` 和部署环境一致；其他支持版本见 `package.json` 的 `engines.node`。

~~~powershell
npm ci
npm run build
node serve.mjs dist/home-viewer/browser 8787
~~~

打开 http://127.0.0.1:8787/ 。不能直接双击 HTML：ES 模块和模型加载需要 HTTP 静态服务。

开发调试：npm start。生产输出目录：dist/home-viewer/browser。整个目录可放入任意 HTTP 静态服务器，也支持子目录部署。依赖和纹理均随包提供，运行时不依赖 CDN。

## 部署到 EdgeOne Pages

通过 Git 仓库导入项目时，将根目录设为包含 `package.json`、`.nvmrc`、`edgeone.json` 的目录。本仓库直接使用根目录 `./`；若放在其他仓库的子目录中，则填写对应子目录。

仓库中的 `edgeone.json` 会覆盖控制台的安装命令、构建命令和输出目录：

| 设置 | 值 |
| --- | --- |
| 框架预设 | Angular |
| 安装命令 | `npm ci --include=dev --no-audit --no-fund` |
| 构建命令 | `npm run build` |
| 输出目录 | `dist/home-viewer/browser` |
| 实际构建 Node.js 版本 | `edgeone.json` 和 `.nvmrc` 均指定 `24.18.0` |

Node.js 版本必须同时满足 Angular 的兼容要求和平台的预装版本要求。平台默认的 `22.21.1` 低于 Angular CLI 22.1.8 的最低要求，会在安装阶段出现 `EBADENGINE` 警告，随后 `ng build` 以退出码 `3` 终止，平台报构建失败（错误码 `18`）。而 `24.15.0` 虽然满足 Angular 要求，但本次 Makers 构建环境无法切换到它，会在安装依赖之前报 `Failed to switch to Node.js 24.15.0`。

Angular 22 支持 Node.js `^22.22.3 || ^24.15.0 || ^26.0.0`。项目选用 Makers 官方预装列表中的 `24.18.0`，在 `edgeone.json` 和 `.nvmrc` 中保持一致。不能依赖 `.nvmrc` 来补救已经失败的 `nodeVersion` 切换；`package.json` 的 `engines` 也仅声明兼容范围，不能替代平台的版本配置。升级时请先核对「项目设置 - Node.js 版本」的可用列表，再同步修改这两个文件。参考 [Angular 版本兼容表](https://angular.dev/reference/versions) 和 [Makers 构建指南](https://pages.edgeone.ai/zh/document/build-guide)。

安装命令显式包含开发依赖，因为 Angular CLI、编译器和 TypeScript 都在 `devDependencies` 中，构建时必须安装。`npm ci` 按已提交的 `package-lock.json` 安装确定的依赖版本。

提交这些配置后重新部署，检查日志中的 Node.js 版本是否为 `v24.18.0`。Angular 构建日志显示的 `dist/home-viewer` 是输出基目录，真正包含 `index.html`、JS、CSS 和 `assets` 的发布目录是 `dist/home-viewer/browser`。部署命令不使用 `npm start` 或 `serve.mjs`，Pages 直接托管构建后的静态文件。配置字段说明见 [Makers edgeone.json 文档](https://pages.edgeone.ai/zh/document/edgeone-json)。

若使用“直接上传”部署，先在本地执行 `npm ci --include=dev` 和 `npm run build`，再上传 `dist/home-viewer/browser` 文件夹，或将该文件夹内的内容压缩为 ZIP 后上传，确保 ZIP 根目录直接包含 `index.html`。不要上传源码目录、`node_modules` 或外层 `dist` 目录。

## 模型

- 独立模型：public/assets/home.glb（单位米，Y 轴向上）。
- 分组与相机：public/assets/project.json。
- 最新原图：public/assets/latest-plan.png。
- 方案二资源：public/assets/scheme-b/{home.glb, project.json, plan.png}；模型版本为 2026-09-14-plan-b。
- 共用窗外树冠资源：public/assets/exterior.glb，由 build_exterior_trees.py 在 Blender 中生成并同步写入两套原生 .blend 文件；更新户型模型后再执行此脚本。树冠独立于家具、房间装修和自动墙面隐藏，不写入家具存档；导出当前 GLB 会包含树木。
- 方案一继续使用 home-simulator:2026-09-14:v1 存储键，方案二使用 home-simulator:scheme-b:2026-09-14:v2；两套模型不共享家具 ID。
- build_scheme_b.py 以方案一的可编辑 .blend 为家具来源，仅复制完整物件并重建建筑；原文件不会被修改。放置坐标、来源和旋转记录在 scheme-b/placement-audit.json。
- 构件 extras：room、rooms、layer、cutaway。
- 可编辑家具 extras：entityId、entityName；浏览器创建独立父组作为物件旋转与移动中心。
- componentNames 记录构件归属；project.json 的 assemblies 明确定义 121 个完整物件、legacyEntities 记录旧版 188 组零件的原始旋转中心，供旧存档迁移。所有构件只属于一个完整物件，共保留 176050 个家具三角面。
- 源 .blend 另附；prepare_web_model.py 基于原 v2 场景更新并重新导出。输出保留原模型的可编辑对象，导出时烘焙程序化基础颜色并合并同一物件构件。

## 设计表达范围

最新图未标尺寸，比例沿既有模型约 58.8 px/m；层高 3m。主卧调整为东侧床头、西侧衣柜；主卫分为坐便、淋浴、短浴缸及洗漱区。厨房根据最新平面采用 U 形操作区，窗边水槽，左侧灶台、回转处电器立柜与不锈钢台面。

客厅南侧落地窗两端按原始户型图补齐通高短实墙，每端暂估0.5m；方案一与原始清水房已同步，方案二原有短墙保留。更新保留既有家具布置。

方案二未标尺寸，参照同户型约 47 px/m 估算，层高同为 3m；次卫北侧狭长空间暂按淋浴家政区表达，图中卧室外的椅形符号按梳妆座椅表达。具体用途与尺寸需深化确认。主卫改为钻石淋浴房、坐便和洗漱柜，家具按新图位置布置。

清水房水泥颜色、盆栽与三维家具为方案表达；不是现场测绘或图片生成效果图的完整复刻。墙体暂不支持拖改，未实现结构检查、家具碰撞约束、设备净空校验、预算计算或自定义外部家具模型导入。模型中既有收纳与隐藏床备选构件仍需深化尺寸。
